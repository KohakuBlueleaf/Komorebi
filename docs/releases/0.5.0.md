# Komorebi 0.5.0

The fifth release of Komorebi: a programming model for the Tensix grid and the X280
cores of a Tenstorrent Blackhole card, with its framework, its device headers and its
dispatchers. It is early development software. Its changes are a handler of a class
that is a hand-written kernel, the chips of a Wormhole Galaxy box as islands, up to 31,
collectives over islands that refuse by name after a give-up until the host clears
them, and a check of every kernel's stack before a load.

## The packages

| Distribution | Version | Imported as | What it carries |
|---|---|---|---|
| `komorebi-tt` | 0.5.0 | `komorebi` | the framework and the `kmr` command; the class and tile compilers; the device and ABI headers; the sources of both dispatchers and the X280 dispatcher's image for cluster 0, prebuilt; the native host module, prebuilt for `komorebi-runtime` |
| `komorebi-runtime` | 0.81.1.4 | `komorebi_runtime` | unchanged since 0.2.0: tt-metal v0.81.1 with our patches, built with its X280 runtime, for a Blackhole P150A |

`pip install "komorebi-tt[runtime]"` installs both and `numpy`; neither `ttnn` nor
`torch` is needed. The runtime is not built again for this release: the `runtime` extra
still asks for `komorebi-runtime` 0.81.1.4 or later, below 0.81.2. The steps, and how
to get the examples and the tutorial's programs, which the wheels do not carry, are on
the [install](../install.md#from-010-the-two-wheels) page. A Wormhole chip, and the
chips of a Galaxy as islands, are run from a clone against a tt-metal tree of your own
([from a clone](../install.md#from-a-clone)), as are two cards. The Komorebi IR is in
the repository and not in either wheel (below, under Experimental).

## New since 0.4.0

- **A handler that is a hand-written kernel.** A class's handler may now be kernel
  files: `@km.handler(km.kernel(movement=..., compute=...))`, or a file for the reader,
  the writer or one compute CPU, beside handlers written in the DSL in the same class.
  Its case calls the files' functions with the handler's decoded parameters, and the
  files are included after the class's header and use its names. `km.Pair` declares a
  buffer pair a hand kernel streams through, numbered with the class's own streams. The
  kernel form and the merge of classes take such a handler; the runtime's form, a
  chain, a dynamic handler, islands, `handlers=` and an overlay are refused at the make
  with the reason. In [33_kernel_handler](../../examples/33_kernel_handler/README.md),
  a gate (example 22's, in blocks of 4 tiles) as a handler beside a DSL handler gives
  the output of the same two files built as a hand program, word for word, at 94.44 µs
  against 94.28 µs on 12 cores
  ([A handler that is a hand-written kernel](../reference/classes.md#a-handler-that-is-a-hand-written-kernel)).
- **Wormhole: the chips of a Galaxy as islands.** A session opens the chips of a
  32-chip Galaxy Wormhole box as islands, up to 31, the pairs taken from the machine's
  Ethernet connections under the one-dimensional fabric forms. The collectives over
  islands, from a kernel and from the host, land their pages in the far leader's L1,
  which writes its own DRAM (about 0.4 GB/s, example 27 on 2 islands); example 28's all-reduce is exact on 2
  and 31 islands. A program whose island build is over NCRISC's 16 KiB of code and
  that never needs the far paths is built near (`KM_ISLAND_NEAR`), each island
  bit-identical to its one-card run on 2 and 31 islands
  ([the near build](../reference/overlays.md#transfers-to-and-from-the-host)). An
  open whose `TT_VISIBLE_DEVICES` hides chips so that tt-metal cannot make one fabric
  mesh of those left raises `km.ChipsHidden`. What runs, with what limit, and on how many chips, row by row, is
  on the new [Wormhole](../reference/wormhole.md) page.
- **Wormhole: loads, classes and tile functions.** A switching (dict) load builds each
  program's own overlays with that program's formats on every group, and refuses by
  name programs that differ in a compute option their parts do not carry. A class added
  to a live run takes its own buffer formats and unpack modes at its own indices. A
  chain's records run in the runtime's form; a 16-bit operand read by `.row()` into a
  float32 result, and a float32 operand copied beside a 16-bit one, now give the
  expected words. A tile function with a matrix product and an operand copied beside
  it, and block-float pages holding a negative zero, are refused by name; the matrix
  unit's sum that cancels to one unit below zero is modelled by
  `komorebi.tools.wormhole_products` ([tile functions on Wormhole](../reference/tile.md#on-wormhole),
  [hazards](../reference/hazards.md#a-products-fp32-sum-that-cancels-to-one-unit-below-zero-on-wormhole)).
- **Collectives after a give-up.** A team now meets and is let go by markers, not
  counts: a count left by a collective given up at its deadline made every later
  meeting of that leader pass one early, and a reduce missed a rank's part now and
  then. A collective over islands given up mid-way leaves its leaders refusing every
  later collective by name until the host has written the tensors again and called
  `run.clear_collectives()`; once the host has seen such a give-up, its own
  collectives (`run.all_reduce()` and the others) are refused at the call, before
  anything is queued. On two Blackhole cards a leader's generation row is now aligned
  to 64 B, where examples 27, 28 and 29 had been given up at their first collective
  ([collectives across islands](../reference/islands.md#collectives-across-islands),
  [hazards](../reference/hazards.md#a-collective-given-up-mid-way)).
- **Classes and the runtime.** A field's fill of a page range takes a stream's
  `block=` and `pattern=` and is read by both movers: on one Wormhole chip a fill into
  the kept fields of 72 cores took 105.6 µs with `block=8, pattern="AAAB"` against
  141.9 to 143.0 µs for the plain fill
  ([A fill on both movers](../reference/classes.md#a-fill-on-both-movers)).
  `km::write_l1(..., km::posted)` writes into another island's L1 without waiting for
  its landing ([islands](../reference/runtime.md#islands)). `total += tile` adds a
  stream's block into sums of several tiles, tile for tile. A run's `stop(timeout)`
  that runs out raises one `km.StopTimeout` naming the step. A class's handler, not
  exclusive, that reads a tensor a command on overlapping cores still writes is warned
  of at `submit` (`km.CommandOrderWarning`). Island runs check each first command's
  placement on the host and say where a tensor's pages lie off its group's islands
  (`km.CrossingWarning`); the link counts are read only when asked
  ([what crossed](../reference/islands.md#what-crossed)).
- **A stack check of every kernel.** Before a load, `Session.load` counts the stack of
  every Tensix kernel image from its linked ELF (the reader, the writer and the three
  compute CPUs, not only the dispatcher's images), with the overlay parts it may call
  at every indirect call and the frames of vector registers the pack thread keeps. A
  kernel with no room left raises `km.StackError` before anything is loaded
  ([a kernel's stack](../reference/host.md#a-kernels-stack)).
- **Fixes.** On Blackhole a core whose reader loaded an overlay could stall just
  after the load and be given up: the reader now loads with its branch predictor off,
  and with example 17 at a kernel buffer of 192,192 B 0 of 160 runs were given up
  where the unchanged kernel was in 35 of 80; it costs about 2 percent a round
  on that example
  ([hazards](../reference/hazards.md#an-overlay-loaded-on-blackhole-with-the-readers-branch-predictor-on)).
  A give-up's recovery resets a core whose control area is gone, which before kept the
  stop from returning and every later open of the process from working
  ([hazards](../reference/hazards.md#a-core-whose-control-area-is-gone-in-the-middle-of-a-run-open)).
  Examples 27 and 28 open a split card with `--islands` again. A prebuild on the
  stand-in card no longer reads the card's clock, and the regression takes as fresh
  only a card list prebuilt off card ([development](../development.md)).

Every table, with its conditions, is on [Measured](../measured.md) and on the
reference pages linked above.

### Projects and examples

These are in the repository, not in the wheels.

- [33_kernel_handler](../../examples/33_kernel_handler/README.md): a hand-written kernel
  as a handler of a class, beside a handler in the DSL in one class and in two merged.
- [examples/ir](../../examples/ir/README.md): programs in the Komorebi IR, its lessons
  and four applications written by hand, each run on its reference interpreter by a
  test.
- [projects/galaxy](../../projects/galaxy/README.md): the token's path of a large
  mixture-of-experts model on the 32-chip Wormhole Galaxy box, piece by piece, each
  piece checked against the model's own reference code run on the host; its table says
  which pieces run on the box.
- [projects/transport](../../projects/transport/README.md): a light-transport matrix
  stored as a hierarchical (block low-rank) matrix, applied on all 120 cores as one
  command, checked against the host's emulation of the same numbers.
- [projects/upscale](../../projects/upscale/README.md): a small super-resolution network
  taking a 512 x 512 frame to 1,024 x 1,024 as one chain command.
- [projects/viewer](../../projects/viewer/README.md): a web page that steers the
  rasterizer's and the ray tracer's interactive loops: the card renders, the server
  streams the frames.
- The [rasterizer](../../projects/raster/README.md) gains an interactive loop,
  textures, direct and indirect lighting, glass, and frames of a chosen width and
  height bounded by memory alone; the [ray tracer](../../projects/raytrace/README.md)
  an interactive loop, a tree built by the surface-area heuristic and traces whose
  cores pull their packets.

## Upgrading from 0.4.0

Nothing a 0.4.0 script imports from `komorebi` was removed. New there: `km.kernel`,
`km.Pair`, `km.StackError`, `km.StopTimeout`, `km.ChipsHidden`,
`km.CommandOrderWarning` and `km.CrossingWarning`.

- **`run.stop(timeout)` raises `km.StopTimeout`** when its timeout runs out, in
  whichever step, where it raised an `EngineTimeout`, a `WaitTimeout` or a
  `KernelFailed` ("never became ready"). It is a `WaitTimeout`, and its message ends
  with the step's own error ([host API](../reference/host.md#run)).
- **A kernel whose stack does not fit is refused at the load** (`km.StackError`), where
  before it ran and could write over its own data.
- **Island runs: `run.crossing_line` is `"check"` by default**, the placement check on
  the host with no card command; the measured line of 0.4.0 is `"measure"`, and
  `"log"`, its earlier name, means the same. Without `log=` on `IslandSession`, the
  check's lines come as `km.CrossingWarning`.
- **New refusals and warnings.** After a collective given up mid-way, write the
  tensors again and call `run.clear_collectives()` before the next collective.
  `session.write` refuses block-float pages holding a negative zero
  (`formats.bfp_canonical` makes each one a plain zero). `run.submit` refuses a
  command whose ranks on an island write a tensor that island holds no page of. A
  command that reads what an earlier one on a shared core writes must be exclusive;
  a class's handler that is not is warned of at `submit`.
- **An island session holds the machine.** Every chip tt-metal sees opens, islands
  only on the cards asked; `TT_VISIBLE_DEVICES` limits which chips open
  ([islands](../reference/islands.md#the-session)).
- **Kernels and the host do not mix across versions.** As before, build your kernels
  against the headers of the version you run; the island table and the collectives'
  words grew in this release.

## Experimental

- **Wormhole**, and the chips of a Galaxy as islands: their rows on the
  [Wormhole](../reference/wormhole.md) page may still change.
- **Kernels written as Python classes and tile functions**, and a handler that is a
  hand-written kernel ([classes](../reference/classes.md)).
- **Three islands or more**: run as one card split into islands, and as the chips of
  a Galaxy; not as more than two Blackhole cards over links.
- **The Komorebi IR**, a work-in-progress module, not released and in neither wheel:
  `src/komorebi-ir/` is a Rust crate with a language for Komorebi programs (`.kom`
  files), its checker, a byte code (`.komc`) and a reference interpreter, with the
  command `komo`. It is frozen at byte code version 6, and nothing in `komorebi-tt`
  depends on it: a Python class is compiled as before. No backend and no frontend is
  part of the build; those written before the language was finished are kept under
  `experiments/ir/reference/`. Beside it are its Python package `komorebi_ir`
  (built with maturin, not published, [packaging/ir](../../packaging/ir/README.md)), a
  VS Code extension and a tree-sitter grammar that colour its text files
  ([packaging](../../packaging/README.md)), and its pages
  ([operations](../ir/operations.md), [checks](../ir/checks.md),
  [run scripts](../ir/run-scripts.md)).

## Known not to work

What Komorebi does not do yet is the README's [TODO list](../../README.md#todo); the
sizes a program works within are its [Limits](../../README.md#limits). In short:

- **Under the dispatcher on a Tensix core:** shared regions; on a split card X280
  threads, ports and ranks.
- **On Wormhole:** X280 threads beyond the one on the dispatcher's core, and on that
  core `kmx_load`, regions, ports and the many-core calls; a card split into islands
  and a writer still over NCRISC's 16 KiB of code at the highest writer level;
  puts and pages into another island's DRAM but the collectives', `km.all_gather` in
  a chain and example 29's chain over islands (each refused by name); code that reads
  or writes Dst through Blackhole's RISC-V window, the ray tracer and the raster
  stages (the build stops). The one-chip census's last pass (2026-11-19): 118 lines pass, 28 are
  refused by name, 13 fail ([Wormhole](../reference/wormhole.md)).
- **Wormhole chips left busy, and overlay fetches that do not land.** An overlay
  part's fetch hung in 4 of 725 runs of `leader_overlay.py`; a run now and then leaves
  a chip's cores busy, or a core's compute unit not ready, until the box is reset. The
  load names a compute unit that is not ready; the causes are not found
  ([hazards](../reference/hazards.md#a-wormhole-chip-whose-cores-stay-busy-after-a-run-open)).
- **An overlay load on Blackhole, its cause.** With the predictor window the stall
  is not seen, but what in the core makes it is not known. Once, with the reader as
  it was, a run ended with one wrong result and no give-up; it was not seen again in
  262 further runs and is not explained. A core whose control area is gone is reset
  and named; what makes its kernel start again is not known.
- More than two Blackhole cards over links; one dynamic run at a time; the lines a
  class refuses ([classes](../reference/classes.md#not-in-this-version)); what a chain
  refuses ([the chain](../reference/chain.md#what-is-refused)).
- Some failures cost a card reset: a core stuck inside a compute unit, a dispatcher
  whose first core stopped, an X280 thread that never returns and polls nothing, a
  process killed with SIGKILL ([recovery](../guides/recovery.md)).

## Supported setup

- One Blackhole P150A, or two joined by their links, with their kernel driver and
  firmware, each card's X280 memory prepared once; programs run in slow dispatch.
- Single Wormhole chips of a Galaxy Wormhole box, and its chips as islands, up to 31
  at one link a pair, from a clone against a tt-metal tree at the pinned version.
- Linux on x86-64 with glibc 2.38 or later (the runtime wheel's tag,
  `manylinux_2_38_x86_64`).
- Python 3.13.
- tt-metal v0.81.1, the version in `packaging/tt-metal.pin`: inside `komorebi-runtime`,
  or a tree of your own when running from a clone (built with the X280 runtime for the
  X280 dispatcher).
