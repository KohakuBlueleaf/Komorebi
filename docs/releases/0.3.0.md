# Komorebi 0.3.0

The third release of Komorebi: a programming model for the Tensix grid and the X280
cores of a Tenstorrent Blackhole card, with its framework, its device headers and its
dispatcher. It is early development software, tested on one card and on two cards
joined by their links. Its central changes are that a program can be written as a
Python class, compiled into the kernels a hand program would have, and that a fixed
sequence of kernels runs as one command, every core going on to the next kernel by
itself.

## The packages

| Distribution | Version | Imported as | What it carries |
|---|---|---|---|
| `komorebi-tt` | 0.3.0 | `komorebi` | the framework and the `kmr` command; the class and tile compilers; the device and ABI headers; the dispatcher's sources and its image for X280 cluster 0, prebuilt; the native host module, prebuilt for `komorebi-runtime` |
| `komorebi-runtime` | 0.81.1.4 | `komorebi_runtime` | unchanged since 0.2.0: tt-metal v0.81.1 with our patches, built with its X280 runtime: the libraries, the kernel runtime tree the cores' compiler uses, the X280 runtime pieces, the program that prepares a card's X280 memory, and a locator |

`pip install "komorebi-tt[runtime]"` installs both and `numpy`; neither `ttnn` nor
`torch` is needed. The runtime is not built again for this release: its sources and the
tt-metal pin have not changed since 0.2.0 (only its README has), so the `runtime` extra
still asks for `komorebi-runtime` 0.81.1.4 or later, below 0.81.2. The steps, and how to get the examples and the
tutorial's programs, which the wheels do not carry, are on the
[install](../install.md#from-010-the-two-wheels) page. Running from a clone against a
tt-metal tree of your own works as before ([from a clone](../install.md#from-a-clone));
two cards run from a clone.

## New since 0.2.0

Grouped as the four concerns of the model, then the cards, the programs and the tools
([README](../../README.md)).

- **Kernels written as Python classes (experimental).** A class deriving `km.Program`
  whose methods are marked `@km.handler` is compiled, when it is made, into the C++
  kernels of a hand program: its streams (`km.Stream`) become the data-movement code
  and the buffers, its fields (`km.L1[...]`) the values a core keeps, its parameters
  the command's words. The arithmetic is tile functions (`@km.tile_function`), which
  the tile compiler turns into the matrix and vector units' instructions. A handler may
  reduce over a group (`km.reduce`), cast to a row or a column (`km.Broadcast`), send
  and handle messages, call an X280 thread, run over islands, and hold inline C++ where
  the lines do not say enough. Classes merge into one program (`km.merge`, or a class
  deriving two), and `run.addon` adds another class to a live run. The made object is
  an ordinary program, loaded with `session.load`. What a handler's lines may be, the
  refusals and what is not in this version are on
  [classes](../reference/classes.md); a tile function's lines on
  [tile functions](../reference/tile.md). The page is marked experimental: its forms
  can still change, and nine examples keep a class beside the hand program
  (`as_class/`).
- **The chain.** Calls written once as records in DRAM run as one command: every core
  goes on to its next record by itself, and a record's input waits for marks from the
  cores that wrote it, not for the host. The host states it with `run.chain`, which
  proves that every input is written before it is read and writes the records once; an
  X280 thread writes the same records with `kmx_chain_record`; a class states it as an
  `@km.chain` method. See [the chain](../reference/chain.md) and
  [29_chain](../../examples/29_chain/README.md).
- **Code placement.** A class or an overlay is added to a run that is loaded and live
  (`run.addon`), compiled against the loaded kernels, and a group, or an X280 thread,
  then loads and calls it ([30_add_overlay](../../examples/30_add_overlay/README.md),
  [overlays](../reference/overlays.md)).
- **Communication.** A dynamic run that gives up on its messages says so
  (`km.MessagesGaveUp`); a bin of messages is also sent by its age (`flush_age`). See [dynamic handlers](../reference/dynamic.md)
  and [broadcasts](../reference/broadcast.md).
- **Islands as a graph of any shape.** A rank may be any number of links away, and a
  link core sends on what is not for its island. One card splits into two to four
  islands as a line, a ring or a 2 x 2 grid with wrap, to develop with one card.
  Collectives run over a tree of the islands' leaders (`km::all_gather`,
  `km::all_reduce`, `km::reduce_to`, `km::broadcast_from`, and `km.all_reduce` in a
  class), and `run.crossings()` counts what crossed a link. A chain runs over islands
  as on one. See [islands](../concepts/islands.md),
  [the islands reference](../reference/islands.md),
  [27_islands_gather](../../examples/27_islands_gather/README.md),
  [28_islands_reduce](../../examples/28_islands_reduce/README.md) and
  [32_islands_l1](../../examples/32_islands_l1/README.md).
- **Block-float weights.** `bfp8_b` and `bfp4_b` tensors (and the A family's `bfp8` and
  `bfp4`) are encoded on the host and read by the cores; a class's products take them.
  See [tile formats](../reference/formats.md).
- **A language model decoding whole tokens on the card.** The
  [decode project](../../projects/decode/README.md) runs Qwen3-1.7B with its real
  weights: the embedding, the 28 layers with attention over a KV cache, the final norm,
  the head and the choice of the token all run on the card, in a loop on one of its
  X280 cores, each token one chain command. In bfloat16, from an 88-token prompt with
  200 tokens generated, it makes 97.6 tokens a second where the official stack
  (tt-metal's `tt_transformers` demo) makes 88.3; with bfp8 and bfp4 weights, the
  official stack's fastest setting, 153.2 against 103.0; the card's clock at 1,350 MHz
  at every read ([table](../measured.md#beside-tt-nn-and-the-official-stack)). Its first
  token is slow: each prompt token is a command of its own, with no batched prefill
  (756 ms for the 88-token prompt in bfloat16).
- **The other programs.** The ray tracer runs a frame as one chain (`--chain`):
  Sponza close in 297.8 ms a frame with its tiles dealt to the cores by the frame
  before's cost ([README](../../README.md#results),
  [raytrace](../../projects/raytrace/README.md#the-frame-as-one-chain)). The
  [nn project](../../projects/nn/README.md) appends kernel calls to a list in DRAM that
  an X280 thread runs. Beside TT-NN on the same card, 32 calls of a matrix product of
  1024 cubed take 43.2 µs a call against 92.4, each side at its fastest setting that
  passes the same check ([README](../../README.md#results)).
- **Tools.** `kmr prebuild` runs a script on the mock card, with no card: its kernels
  are built and its loads checked as the card would, and its reads give zeros. Two fast
  checks, `python -m komorebi.tools.host_check` (no card) and
  `python -m komorebi.tools.card_check`, run the checks a change needs. See
  [run off the card](../guides/run-off-the-card.md). What can go wrong in a program
  that builds without complaint, and the guard for each, is on
  [hazards](../reference/hazards.md).

The repository grew to thirty-two examples (numbers 27 to 32 are new: the gather and
the reduce across islands, the chain, code added to a live run, the README's SwiGLU
layer as a class, an L1 tensor moved across islands), and `experiments/language/`
holds the measurements behind the class and tile compilers. Every table, with its
conditions, is on [Measured](../measured.md).

## Upgrading from 0.2.0

The calls of the host API take the arguments they took (new ones come after them), but
modules moved into packages, and the device headers into folders. What to know:

- **Module paths.** These modules of 0.2.0 moved, without a module left at the old
  path, so an import of the old path fails:

    | 0.2.0 | 0.3.0 |
    |---|---|
    | `komorebi.build` | `komorebi.builder.flags` |
    | `komorebi.channel` | `komorebi.device.channel` |
    | `komorebi.dram` | `komorebi.device.dram` |
    | `komorebi.native` | `komorebi.device.native` |
    | `komorebi.tensor` | `komorebi.device.tensor` |
    | `komorebi.insn_check` | `komorebi.program.checks.instructions` |
    | `komorebi.movement` | `komorebi.program.movement` |
    | `komorebi.overlay` | `komorebi.program.overlay` |
    | `komorebi.programs` | `komorebi.program.several` |
    | `komorebi.thread` | `komorebi.program.thread` |
    | `komorebi.island_session` | `komorebi.islands.session` |
    | `komorebi.run` | `komorebi.session.run` |
    | `komorebi.state` | `komorebi.session.state` |
    | `komorebi.power` | `komorebi.bench.power` |
    | `komorebi.stats` | `komorebi.bench.stats` |

    The names the package exports (`km.Session`, `km.Program`, `km.Pattern`, the
    errors) are where they were.
- **`km.Session` is in `komorebi.sessions`.** `komorebi.session` is now a package and
  no longer holds `Session`: write `km.Session`, or import it from
  `komorebi.sessions`.
- **`km.Program` is the class base.** It derives the `Program` of 0.2.0
  (`komorebi.program.Program`) and takes the same arguments, so
  `km.Program(name, kernels=folder)` describes a hand program as before; a subclass
  with handler methods is a program written as a class.
- **Device headers moved into folders** under `komorebi/device/`: `core/`
  (`km_program.hpp`, `km_x280.hpp`, ...), `movement/` (`km_movement.hpp`,
  `km_broadcast.hpp`, `km_port.hpp`), `messages/` (`km_messages.hpp`), `overlays/`
  (`km_overlay.hpp`), `tensors/` (`km_ask.hpp`) and `links/`. `km_worker.hpp` stays
  where it was. A kernel's `#include` of an old path fails; the examples show the new
  ones.
- **Kernels and the host do not mix across versions.** As before, build your kernels
  against the headers of the version you run, from the wheels or a clone of one
  version.

## Experimental

- **Kernels written as Python classes and tile functions.** The page and its forms may
  still change ([classes](../reference/classes.md)).
- **Three or four islands.** They have run only as one card split into islands, not
  over a link.
- **A clock of 1,750 MHz** for the X280 clusters is an option that loses loads under a
  full matrix load ([host API](../reference/host.md#session)).

## Known not to work

What Komorebi does not do yet is the README's [TODO list](../../README.md#todo); the
sizes a program works within are its [Limits](../../README.md#limits). In short:

- Anything but Blackhole P150A cards, one or two, in slow dispatch; grids of up to 128
  cores in at most two multicast panels per card. Two cards run from a clone, as 236
  ranks.
- More than two cards over links
  ([the islands reference](../reference/islands.md#what-is-not-built)).
- One dynamic run at a time, and not the dynamic handlers of two programs in one run;
  no order between messages; a body of more than one 4 KiB page
  ([dynamic handlers](../reference/dynamic.md#not-in-this-version)).
- The lines a class refuses, each with the way round, are on
  [classes](../reference/classes.md#not-in-this-version); what a chain refuses on
  [the chain](../reference/chain.md#what-is-refused).
- The decode project has no batched prefill: a prompt's tokens are one command each.
- At most 64 commands in flight, ten 32-bit argument words per command, handlers 1 to
  239.
- Some failures cost a card reset: a core stuck inside a compute unit, a dispatcher
  whose first core stopped, an X280 thread that never returns and polls nothing, a
  process killed with SIGKILL ([recovery](../guides/recovery.md)).
- Nothing reads a core's registers or a program's variables on the card.

## Supported setup

- One Blackhole P150A, or two joined by their links, with their kernel driver and
  firmware, each card's X280 memory prepared once; programs run in slow dispatch.
- Linux on x86-64 with glibc 2.38 or later (the runtime wheel's tag,
  `manylinux_2_38_x86_64`).
- Python 3.13.
- tt-metal v0.81.1, the version in `packaging/tt-metal.pin`: inside `komorebi-runtime`,
  or a tree of your own built with the X280 runtime when running from a clone.
