# Komorebi 0.4.0

The fourth release of Komorebi: a programming model for the Tensix grid and the X280
cores of a Tenstorrent Blackhole card, with its framework, its device headers and its
dispatchers. It is early development software. Its two changes are a second dispatcher,
which runs on one Tensix core of the grid and needs no X280, and with it a first part of
Wormhole: a session on one Wormhole chip, and islands of Wormhole chips.

## The packages

| Distribution | Version | Imported as | What it carries |
|---|---|---|---|
| `komorebi-tt` | 0.4.0 | `komorebi` | the framework and the `kmr` command; the class and tile compilers; the device and ABI headers; the sources of both dispatchers and the X280 dispatcher's image for cluster 0, prebuilt; the native host module, prebuilt for `komorebi-runtime` |
| `komorebi-runtime` | 0.81.1.4 | `komorebi_runtime` | unchanged since 0.2.0: tt-metal v0.81.1 with our patches, built with its X280 runtime, for a Blackhole P150A |

`pip install "komorebi-tt[runtime]"` installs both and `numpy`; neither `ttnn` nor
`torch` is needed. The runtime is not built again for this release: the `runtime` extra
still asks for `komorebi-runtime` 0.81.1.4 or later, below 0.81.2. The steps, and how
to get the examples and the tutorial's programs, which the wheels do not carry, are on
the [install](../install.md#from-010-the-two-wheels) page. From the wheels both
dispatchers run on a P150A, and `kmr prebuild --arch wormhole_b0` builds a script's
kernels for Wormhole. A Wormhole chip itself is run from a clone against a tt-metal
tree of your own ([from a clone](../install.md#from-a-clone)), as are two cards.

## New since 0.3.0

- **The dispatcher on a Tensix core.** `km.Session(dispatcher="tensix")` puts the
  dispatcher on the grid's last Tensix core and runs the program on the others: 119
  cores on a P150A, 79 on a Wormhole chip. It is the default where the build has no
  X280 runtime and on Wormhole; `KMR_DISPATCHER` names it for a script, and
  `session.dispatcher` and `session.ranks` say which one runs and on how many cores.
  It takes commands from the host's ring, from the command rings of X280 threads, from
  the stream and graph engines, which run on its own core, and from another island,
  hands them to the cores and returns their events. It serves plain and exclusive
  commands with deadlines, the chain, overlays and add-ons, several programs in one
  run, the job queue, streams and graphs (host-fed and resident), dynamic handlers on
  one island and across islands, a command given up at its deadline with the run going
  on, the reset and reload of one core, the watch and the trace. On Blackhole it also
  serves X280 threads on clusters 1 to 3 with their command rings, commands to a
  thread, X280 ports and a dynamic run's X280 ranks; cards as islands, a card split
  into islands with one dispatcher an island, and an engine's graph across islands.
  What it does not serve is refused by name (`km.NotServed`) at the load or the call:
  shared regions, and on a split card X280 threads, ports and ranks. The whole card
  list but the two lines with shared regions passes under it on Blackhole: 92 lines on
  one card and 22 on two. See
  [the two dispatchers](../../README.md#the-two-dispatchers-and-wormhole), the
  [host API](../reference/host.md#session) and
  [islands under the Tensix dispatcher](../reference/islands.md#under-the-tensix-dispatcher).
- **Wormhole, a first part.** A session opens one Wormhole chip, its facts read from
  the device (the 8 x 10 grid, L1, 32 buffer indices, 12 DRAM banks, the tick rate),
  under the dispatcher on a Tensix core. Kernels in C++ and as Python classes run as
  plain commands, with tensor reads and writes; overlays, classes added to a live run,
  several programs and program switches; a chain; dynamic handlers; one thread's C on
  the dispatcher's own core. Tile functions are compiled to Wormhole's own instruction
  words and give Blackhole's results word for word; the attention project and the
  raster project's fill run and write Blackhole's output. Islands of Wormhole chips run
  in part: commands across islands and a dynamic run's deliveries, exact on two and
  four chips. Of 159 example, tutorial and test lines run on single chips of a Galaxy Wormhole
  box, 120 pass, 28 are refused by name (they need an X280, or a writer over the chip's
  16 KiB of code) and 11 fail (below). `kmr prebuild --arch wormhole_b0 <script>`
  builds a script's kernels for Wormhole on a machine with no Wormhole chip. What runs
  and what does not, line by line, is in the
  [README's table](../../README.md#the-two-dispatchers-and-wormhole); the chip's own
  rules are on [hazards](../reference/hazards.md) and
  [tile functions on Wormhole](../reference/tile.md#on-wormhole).
- **Checks that name a failure before it happens.** A load under the Tensix dispatcher
  measures each of the dispatcher's images against its stack and raises
  `km.DispatcherStackError` when one has no room
  ([the dispatcher's stack](../reference/host.md#a-kernels-stack)). On Wormhole
  the dispatcher reads each core's compute unit at its start and after its reset of a
  core: one that is not ready is named in a `km.StartError` with what clears it
  ([reset](../concepts/reset.md)). A stop that fails while a run is failing now tells
  both errors and the result block it read.
- **Fixes.** A 64-bit read of the wall clock on Wormhole could be 2^32 ticks ahead
  ([hazards](../reference/hazards.md#time-taken-from-the-clock-a-wormhole-chip-reports));
  a program's circular buffers and an overlay's images are laid out for the open chip,
  not for a P150A; examples, tutorials and projects plan over the session's ranks, not
  the grid's 120 cores; a script that printed a false verdict now exits 1.
- **Tools.** `card_check --prebuild` builds a list's kernels on the stand-in card
  first and counts a line only when it built ([development](../development.md));
  `kmr dram-check` checks a card's DRAM ([install](../install.md#checking-a-cards-dram));
  a session says what state a card is in before it opens it.

Every table, with its conditions, is on [Measured](../measured.md).

## Upgrading from 0.3.0

The calls of the host API take the arguments they took; new ones come after them.

- **The default dispatcher is unchanged on a P150A**: the X280 dispatcher, where the
  runtime has its X280 part. A program written for it runs as before.
- **Plan over `session.ranks`, not the grid.** Under the dispatcher on a Tensix core a
  program has one core fewer than the grid (119 on a P150A). A script that names all
  120 cores does not fit there; the examples now take their group from the session.
- **Kernels and the host do not mix across versions.** As before, build your kernels
  against the headers of the version you run.

## Experimental

- **The dispatcher on a Tensix core** and **Wormhole**: new in this release; their
  limits are the README's table and may still change.
- **Kernels written as Python classes and tile functions**
  ([classes](../reference/classes.md)).
- **Three or four islands**: run as one card split into islands, and as four Wormhole
  chips; not as four cards over links.

## Known not to work

What Komorebi does not do yet is the README's [TODO list](../../README.md#todo); the
sizes a program works within are its [Limits](../../README.md#limits). In short:

- **Under the dispatcher on a Tensix core:** shared regions; on a split card X280
  threads, ports and ranks.
- **On Wormhole:** X280 threads beyond the one on the dispatcher's core, and on that
  core `kmx_load`, regions, ports and the many-core calls; a card split into islands
  and any program whose writer is over NCRISC's 16 KiB of code (`swiglu_direct.py`);
  pages into another island's DRAM; the raster project's stages on the cores and the
  ray-tracing project (ten of the eleven failing lines).
- **A Wormhole core left with its compute unit not ready.** Rarely, after a hang, a
  core's compute side no longer runs a kernel; the cause is not known. The run names
  the core at the next load; no reset by software clears it, a reset of the card does
  ([recovery](../guides/recovery.md#when-a-card-reset-is-still-the-only-way)).
- **A broadcast with overlays under a large kernel buffer, on Blackhole.**
  `examples/17_leader_overlay/leader_overlay.py --rect 0,0,1,10 --choices cycle` under
  the dispatcher on a Tensix core has a command given up at its deadline in 24 of 90
  runs when the session's kernel buffer is 197,184 B, and in none of 160 runs at
  135,168 B or below: the last core of its broadcast column stops in its reader and the
  column waits for it. The dispatcher gives the command up and recovers the core. The
  cause is not found yet.
- More than two cards over links; one dynamic run at a time; the lines a class refuses
  ([classes](../reference/classes.md#not-in-this-version)); what a chain refuses
  ([the chain](../reference/chain.md#what-is-refused)).
- Some failures cost a card reset: a core stuck inside a compute unit, a dispatcher
  whose first core stopped, an X280 thread that never returns and polls nothing, a
  process killed with SIGKILL ([recovery](../guides/recovery.md)).

## Supported setup

- One Blackhole P150A, or two joined by their links, with their kernel driver and
  firmware, each card's X280 memory prepared once; programs run in slow dispatch.
- Single Wormhole chips, and two or four as islands, of a Galaxy Wormhole box, from a
  clone against a tt-metal tree at the pinned version.
- Linux on x86-64 with glibc 2.38 or later (the runtime wheel's tag,
  `manylinux_2_38_x86_64`).
- Python 3.13.
- tt-metal v0.81.1, the version in `packaging/tt-metal.pin`: inside `komorebi-runtime`,
  or a tree of your own when running from a clone (built with the X280 runtime for the
  X280 dispatcher).
