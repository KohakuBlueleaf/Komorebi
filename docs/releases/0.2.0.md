# Komorebi 0.2.0

The second release of Komorebi: a programming model for the Tensix grid and the X280
cores of a Tenstorrent Blackhole card, with its framework, its device headers and its
dispatcher. It is early development software, tested on one card and on two cards
joined by their links. Its central change is that a program can now move the code as
well as the data and the thread: code that is not in a core's kernels is loaded into its
memory when it is needed, and two cards run as one program.

## The packages

| Distribution | Version | Imported as | What it carries |
|---|---|---|---|
| `komorebi-tt` | 0.2.0 | `komorebi` | the framework and the `kmr` command; the device and ABI headers; the dispatcher's sources and its image for X280 cluster 0, prebuilt; the native host module, prebuilt for `komorebi-runtime` |
| `komorebi-runtime` | 0.81.1.4 | `komorebi_runtime` | tt-metal v0.81.1 with our patches, built with its X280 runtime: the libraries, the kernel runtime tree the cores' compiler uses, the X280 runtime pieces, the program that prepares a card's X280 memory, and a locator |

`pip install "komorebi-tt[runtime]"` installs both and `numpy`; neither `ttnn` nor
`torch` is needed. The `runtime` extra now asks for `komorebi-runtime` 0.81.1.4 or
later: that build carries the X280 clock rows the session's default clock needs.
`kmr setup` then fetches the cores' compiler and prepares the card's X280 memory, once.
The steps, and how to get the examples and the tutorial's programs, which the wheels do
not carry, are on the [install](../install.md#from-010-the-two-wheels) page. Running from
a clone against a tt-metal tree of your own works as before ([from a
clone](../install.md#from-a-clone)); two cards run from a clone.

## New since 0.1.0

Grouped as the four concerns of the model, then the card and the cards
([README](../../README.md)).

- **Code placement.** An *overlay* is code built on the host and kept in DRAM; a core
  *loads* it into a *slot* of its own L1 when it is first needed, and *calls* it. A
  handler, a message, a leader's cast or the word of a pull's answer from an X280 core
  can name the overlay, so the code goes where the work is. Several programs share one
  run, each on its own group of cores or all of them on every core, and a group changes
  program inside a live run, from the host (`run.load`) or from an X280 thread
  (`kmx_load`). A program can also be written in the runtime's form (`km_program` in
  place of `kernel_main`), under kernels the runtime owns. The code and its slots sit
  below 1 MB of L1, and a program that does not fit is refused at load with a table of
  its budget. See [overlays](../reference/overlays.md).
- **Communication.** A message carries a body of up to 4 KiB beside it, and names its
  handler, with several dynamic handlers in one program and their bodies as overlay
  parts loaded where the message lands. X280 cores can be ranks of a dynamic run. A
  broadcast carries a word, with tiles or alone, so a leader can decide what its group
  does next. Kernels read and write a tensor's pages through `km::read_pages` and
  `km::write_pages` on a `km::Tensor`, and put a run of pages without waiting
  (`km::put_pages`, `km::put_wait`); the page calls reach a page wherever it is
  held, on this card or on another. A program can give each data-movement CPU its NoC
  (`noc` of the program). See [dynamic handlers](../reference/dynamic.md) and
  [Movement](../reference/movement.md).
- **Execution control.** The host, a graph and a stream can command a work cluster's
  thread, and a pull's answer carries a word. A thread reads and writes
  any DRAM bank, or a tensor another card holds, through the Tensix cores (`kmx_fetch`,
  `kmx_store`) at the cores' rate. The command ring holds 64 commands in place of 16,
  and a command can carry a block of up to 1,024 bytes. See
  [X280 threads](../reference/threads.md).
- **The host at the link's speed.** Tensor reads and writes, and L1 tensors, go through
  the host channel of the card's PCIe tile: a 20 MiB frame is read in 7 ms inside a
  run, where the device API took 10 s.
- **A run survives a stuck core.** `run.inspect` shows a running core's state and its
  wait; a command that misses its deadline is given up and the run goes on; a core that hangs is reset and loaded again with its kernels while the others
  run, by the dispatcher or by the host. See [recovery](../guides/recovery.md).
- **Two cards as one program.** Each card is an *island* with its own grid and
  dispatcher, and a session opens several cards (or splits one into islands). Ranks stay
  flat across islands, the host places each tensor by a hint, and commands, pages, parts
  of a page, messages, reduces and broadcasts cross the links between the cards, which
  two cores of each card serve. The kernels of a program written for one card run on
  two unchanged. See [islands](../concepts/islands.md) and
  [the islands reference](../reference/islands.md).
- **The X280 clusters at 1,350 MHz** by default (1,000 MHz on a runtime without the
  clock rows), and a clock of 1,250 or 1,500 MHz on request.

What it was used for and measured on: a linear layer `Y = X W` in bfloat16 over two
cards runs 1.90 times faster than on one card at 8192 cubed and 1.95 times faster at
16,384 cubed with W gathered on both cards, and the matrix products, attention and the
rasterizer also run over two cards. The programs' results are in the README's table
([Measured](../../README.md#results)), the run behind every row on each program's
page. The repository grew to twenty-six examples (numbers 12 to 26 are new: overlays,
several programs, messages with a body, X280 ranks, a kernel written for islands) and a
tutorial of 52 lessons, and `experiments/` holds the measurements behind the design.

## Upgrading from 0.1.0

No call of the `komorebi` package is removed or renamed: every public function, class
and method of 0.1.0 is still there with the arguments it took (new ones come after
them), and every name of the device headers is still defined, one internal helper of
the dispatcher aside. The kernels of `05_forward` are those of 0.1.0. What to know:

- **Handlers are objects of their program.** `Program.handler(name)` returns a `Handler`,
  an `int` that also names its program, which `submit`, `Graph.command` and a stream
  take; a number or a name still works for the run's first program. A command's
  header carries the program's place in the run in a new field (bits 24 to 31).
- **`handlers_from_header` moved** from `komorebi.program` to `komorebi.abi`; the old
  name still imports.
- **The command ring has 64 slots, not 16** (`KM_RING_SLOTS`), and the control block
  after it is derived from that count. Kernels, the dispatcher and the host module of
  0.1.0 and 0.2.0 do not mix: use the wheels, or a clone, of one version and build your
  kernels against its headers. Up to 64 commands can be in flight.
- **The default X280 clock is 1,350 MHz**; on a runtime older than 0.81.1.4 the session
  falls back to 1,000 MHz and says so.
- **The runtime numbers above 239 are the runtime's, as before, and more are used:**
  240 loads code, 241 to 248 serve the host channel, copies and pages. The handlers of a
  program stay 1 to 239.
- **The kernels of the repository read and write tensor pages through the page calls.**
  Code written with `TensorAccessor` and `noc_async_read_page` runs as it did on one
  card; to read or write pages that another card holds, use `km::read_pages` and
  `km::write_pages`.

Correction (2026-11-18): "no call is removed or renamed" held at 0.2.0. Since then these
module paths of 0.2.0 moved without a module left at the old path, and an import of them
fails on main:
`komorebi.channel`, `komorebi.dram`, `komorebi.insn_check`, `komorebi.island_session`,
`komorebi.movement`, `komorebi.native`, `komorebi.overlay`, `komorebi.power`,
`komorebi.programs`, `komorebi.run`, `komorebi.state`, `komorebi.stats`,
`komorebi.tensor` and `komorebi.thread`; `komorebi.build` is `komorebi.builder`.

## Experimental

- **Three or four islands.** They have run only as one card split into islands, not
  over a link; a line of islands on one card forwards through those between.
- **A clock of 1,750 MHz** for the X280 clusters is an option that is not stable under
  a full matrix load: the dispatcher trapped in 9 of 18 runs.

## Known not to work

What Komorebi does not do yet is the README's [TODO list](../../README.md#todo); the
sizes a program works within are under it. In short:

- Anything but Blackhole P150A cards, one or two, in slow dispatch; grids of up to 128
  cores in at most two multicast panels per card, and one harvesting pattern has been
  run. Two cards run from a clone, with 236 ranks.
- More than two cards over links; collectives across islands as calls (an all-gather
  and an all-reduce are made from puts); tensors of a page size set by the command, or
  a range of one DRAM bank, on another island.
- One dynamic run at a time, and not the dynamic handlers of two programs in one run;
  no order between messages; a message cannot ask for a DRAM fetch; a switch of a
  dynamic program; a program's buffers do not survive a switch of program.
- One thread per X280 work cluster, three at most; messages over one link of the four
  by default.
- At most 64 commands in flight, ten 32-bit argument words per command, handlers 1 to
  239.
- Some failures cost a card reset: a kernel that leaves a compute unit running, a
  packer that writes past its buffer, an X280 thread that never returns and polls
  nothing, a dispatcher whose first core stopped executing, a process killed with
  SIGKILL. The compute kernel's waits between its own three threads and the NoC
  barriers have no timeout.
- A stalled core that later commands in flight also hold is not recovered: the run ends
  in the time-out as in 0.1.0, since its reset would drop those commands.
- Nothing reads a core's registers or a program's variables, and tt-metal's watcher
  cannot run while the X280 runtime is open.
- `kmr build host` and `kmr build pymodule` need a tt-metal tree with the targets of the
  tt-x280-dispatch project ([development](../development.md#known-limitations)); the
  wheels need neither.

## Supported setup

- One Blackhole P150A, or two joined by their links, with their kernel driver and
  firmware, each card's X280 memory prepared once; programs run in slow dispatch.
- Linux on x86-64 with glibc 2.38 or later (the runtime wheel's tag,
  `manylinux_2_38_x86_64`).
- Python 3.13.
- tt-metal v0.81.1, the version in `packaging/tt-metal.pin`: inside `komorebi-runtime`,
  or a tree of your own built with the X280 runtime when running from a clone.
