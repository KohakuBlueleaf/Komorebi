# Komorebi 0.6.0

A minor release after [0.5.3](0.5.3.md). New are a make option that enters each
handler of a class out of line, and a build check of a buffer pair's halves. Fixed are
tensors of pages past 512 KiB through the host channel, the handler of a graph's or a
stream's command in a run of a merged program, and where a reset core's give-ups are
said. Two changes are seen by code that ran on 0.5.3: a class's build folders are now
in the cache directory, so every class builds once again, and the text of a
`CommandTimeout` with a `recovered` part ends with a new sentence (below, under
upgrading).

## The packages

| Distribution | Version | Imported as | What it carries |
|---|---|---|---|
| `komorebi-tt` | 0.6.0 | `komorebi` | as in 0.5.0 to 0.5.3 |
| `komorebi-runtime` | 0.81.1.4 | `komorebi_runtime` | unchanged since 0.2.0: tt-metal v0.81.1 with our patches, built with its X280 runtime, for a Blackhole P150A |

`pip install -U "komorebi-tt[runtime]"` takes 0.6.0; the runtime is not built again
and the `runtime` extra still asks for `komorebi-runtime` 0.81.1.4 or later, below
0.81.2 ([install](../install.md#from-010-the-two-wheels)).

## New since 0.5.3

- **Handlers entered out of line.** A handler's body lies in the frame the handlers are
  chosen in, so a handler entered from there, a hand kernel's call above all, starts
  under the locals of every other handler. A class made with `out_of_line=True` gives
  each resident handler's case body a function of its own that the compiler never
  inlines; a `break` that left the case returns. It costs a call a command and code. In
  a mock build, a class whose `km.kernel` handler calls a chain of 976 B, merged with a
  class whose handler holds 480 B of locals, needs 1,344 B of stack on mover B where it
  needed 1,808, for 4,404 B more code in all. The option has a build folder of its own,
  and the classes of a merge must give one value. The default is as before
  ([Making and calling](../reference/classes.md#making-and-calling)).
- **A buffer pair's halves checked at the build.** A half of a `km::BufferPair` is a
  buffer index below 32; a stream with a half of 32 or above gives up on the card
  (`bad_item` at `movebuffer`). Built with `KM_PAIR_CHECK` 1 (`defines=` of a
  `km.Program`), a pair made in a constant initializer with such a half fails the build
  instead, the compiler's error naming the index under the line of the pair. A pair
  made at run time is not checked; `KM_PAIR_CHECK` 0, the default, builds as before,
  byte for byte ([movement](../reference/movement.md)).

## Fixed since 0.5.3

- **A tensor of pages past 512 KiB, made before a load, is written and read.** Without
  a run, a transfer of pages over 16 KiB goes through the transfer kernel. Its buffer
  was given 16 B pages, and tt-metal counts a buffer's pages in 16 bits, so a page of
  512 KiB made 65,544 of them and tt-metal ended the launch ("number of CB pages 65544
  is greater than 65535"). The buffer is now one page. Whether it fits is measured
  below the session's own L1 buffers and the launch's report; a page that does not fit
  goes through the device API, and a page range of such a tensor without a run is
  refused with both sizes (`km.ChannelError`)
  ([the host channel](../reference/host.md#the-host-channel)).
- **A live write in pieces of a tensor with fewer pages than DRAM banks.** While a run
  is loaded, a page wider than the run's chunk is written in pieces through a view of
  the tensor. The view counted its pages as if the tensor's pages were whole rows of
  banks, so such a write (one page of 512 KiB in a run of 16 KiB chunks) was refused
  for a bound it keeps. The view now counts the pages every bank holds.
- **A graph's and a stream's command settle their handler against the run.** A
  command of a graph, and a stream's `submit` and `enqueue`, keep the handler they were
  given and settle its number and program field against the run's programs when they
  are uploaded (`run.upload`) or run host-fed (`run.run_hostfed`), as `run.submit`
  does. A source's own handler in a run of a merged program was written as its own
  number, so it queued another handler of the merged program; it is now its number
  there, and a graph or stream built for one run is right in another. A plain number is
  written as given ([graphs](../graphs.md#building-a-graph),
  [streams](../streams.md#building-a-stream)). `restart` of a graph uploaded and never
  started now says so and names `start`.
- **A reset core's give-ups are said where they are read.** Under `recover=True` the
  dispatcher reads every core of a given-up command's group at the deadline, then
  resets the cores still in it; the reset writes the core's control area again, so
  `run.state()` after the stop no longer lists the give-ups before it. The
  `CommandTimeout`'s text now says so after its `recovered` part: the gave-up words it
  names were read before the reset and are kept in its cores, `run.given_up(handle)` and
  `run.recoveries` ([recovery](../guides/recovery.md)).
- **`kmx_serve`'s comment and reference.** They say it serves until the lead has ended
  `kmx_main` and, in a thread that also serves commands, stopped serving them
  ([threads](../reference/threads.md)).

## Upgrading from 0.5.3

- A class's build folders are now in the cache directory (`KMR_CACHE`, else
  `build/komorebi/` in a checkout, else `~/.cache/komorebi`), under
  `classes/<folder>-<path hash>/`, one for each folder of class sources. A `build/`
  folder beside a class's source is no longer written or read and may be deleted.
  A body's relative include and a hand kernel's file are now written as absolute
  paths, so the generated text changes and each class builds once again
  ([Making and calling](../reference/classes.md#making-and-calling)).
- A `CommandTimeout` with a `recovered` part, and the `text` of `run.recoveries`, end
  with the new sentence above: code that matched the end of that text changes.
- `out_of_line` is now one of the make's own keywords, so a tensor parameter of that
  name is refused at the parameter (rename it); an int or float word of that name is
  a command word, as before.
- A graph or stream whose commands give a class's handler is now settled against the
  run; one given plain numbers is written as before. As before, build your kernels
  against the headers of the version you run.
